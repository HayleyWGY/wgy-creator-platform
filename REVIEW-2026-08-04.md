## 2. Your question: review before or after hooking up the Stripe webhooks?

**Short answer: you've done the right thing by reviewing now (before). Build the webhook next, then do a *focused* review of just the webhook and its interactions — not another full-app pass.**

Here's the reasoning, because the "safest route" depends on *what* you review *when*:

**Why the general review belongs before the webhook (now):**
- The webhook doesn't exist in a vacuum — it depends on infrastructure that this review just verified is sound: the `account-token` + `set-password` flow (for the "set your password" email on new subscribers), the `getPayingSession` paywall (which the webhook will start *driving* when it flips people to `payment_failed`), and the rate limiter. Building the webhook on a *verified* baseline means any bug you find afterwards is almost certainly in the webhook itself, not underneath it.
- The paywall is already load-bearing. `getPayingSession` enforces `payment_failed` at the API today — but nothing *sets* that status yet. The moment the webhook does, that status transition becomes real for members. You want the thing that reads the status proven correct (it is, now) before the thing that writes it goes live.

**Why the webhook needs its own review after it's built:**
- Webhooks have failure modes a whole-app review doesn't stress: **duplicate delivery** (Stripe sends the same event more than once — the handler must be idempotent), **out-of-order events** (a `subscription.deleted` can arrive before the `payment_failed` that preceded it), **replay**, and the **account-creation path** (creating a real member account with real PII from an external trigger is the single most sensitive write in the app). These deserve a concentrated pass, not a paragraph inside a 66-route sweep.
- If you instead build the webhook and *then* do another full review, the webhook's subtle issues get diluted across the whole surface and are easy to miss.

**So the safe sequence is:**
1. ✅ This review (baseline verified — done).
2. Build the Stripe webhook event logic against that baseline.
3. **Focused webhook review** — idempotency, replay, event ordering, the account-creation path, the status-flip paths, and a signature-verification edge-case check. I can do that as a targeted pass.

**One reassurance:** building the webhook now is safe from a data-exposure standpoint. Per your own migration notes, the handler no-ops for Stripe customers not yet in the DB, so wiring it up early won't pull member data through before you're ready to migrate. And everything it needs (the token/password-setup infra) is already built and verified. There's no dependency reason to wait.

**A question for you on this** (see §6): when the webhook creates a new member on `subscription.created`, do you want that to be *gated behind a go-live flag* until you flip it on? Your earlier notes mentioned this. It matters for the webhook's design and I'd want it decided before it's built.

## 4. New observations from this pass

None are launch-blocking. N1 and N3 are worth doing before the Stripe webhook; the rest can wait.

### N1 (medium) — Duplicate, divergent Stripe portal routes
There are **two** billing-portal routes doing almost the same thing:
- `app/api/billing/portal/route.ts` → returns to `/home`
- `app/api/stripe/portal/route.ts` → returns to `/payment-updated`

Both are IDOR-safe (customer id comes from `session.user.id`, never client input), both gate correctly with `getActiveSession`. But this is the exact "two implementations of one feature" pattern that has caused real bugs in this repo (the two comment routes, the two like routes). If one gets a security fix later and the other doesn't, that's the regression. **Consolidate to one before the webhook lands**, since the webhook will reference the recovery flow and you want a single source of truth. Decide which return URL is correct (`/payment-updated` reads like the intended one) and delete the other.

### N2 (low, but exactly the pattern you're trying to kill) — `failedLoginAttempts` is now a dead column with a misleading comment
H5 replaced the hard account-lockout with progressive backoff. But `failedLoginAttempts` is still incremented on failure (`auth.ts:184`) and cleared on success — and **nothing reads it any more** to lock anyone. `lockedUntil` is likewise only ever cleared, never set. Meanwhile a comment in `auth.ts` still refers to "the existing DB-backed lockout (5 failures → 15 min) below," which no longer exists.

Not a security hole — backoff covers the intent. But it's a dead control plus a comment describing a guard that isn't there, which is precisely the class of thing this codebase has been working to eliminate. **Either** remove the column writes and the stale comment, **or** (my lean) keep a real per-account lock as a *backstop* with a genuinely high threshold, so there's defence if Redis (which the backoff depends on) is down. Pick one and make the code and comment agree.

### N3 (medium — verify before launch) — The onboarding idempotency migration may not be applied to production
`lib/onboarding-drip.ts` now relies on the `@@unique([creatorId, templateId])` constraint to prevent double-sends: it `create`s the "sent" row as a claim and treats P2002 as "someone else already sent this." The constraint is in `schema.prisma` and there's a migration file (`20260727120000_add_onboarding_unique_and_indexes`). **But a migration in the repo is not a migration in the database** — the commit that introduced it was titled "migration NOT applied," and I can't confirm from code whether `prisma migrate deploy` has since run against production.

If it hasn't, the drip's idempotency silently doesn't work: two concurrent runs both insert successfully and both send. At a single daily cron the concurrency risk is low, but a retry or a manual re-run could double-DM migrating members on day one. **Checklist item: confirm the migration is applied to prod** (over `DIRECT_URL`, per the known pooler-hang issue) before the full migration.

### N4 (low) — `failed-payments` GET can be slow and has no timeout guard
The admin failed-payments page fetches up to 100 past-due subscriptions and then does **two sequential Stripe API calls per subscription** (`customers.retrieve` + `invoices.list`) — up to ~200 serial round-trips. Admin-only and infrequent, so not urgent, but with a real backlog of past-due accounts this could exceed even the Vercel Pro 60s function timeout, and there's no rate limit on it. Consider `Promise.all` with a concurrency cap, or paginating the UI. Note for when billing is live, not now.

### N5 (low, UX) — Fallback poll can truncate loaded scrollback
The 10s fallback poll fetches only the newest page. If a member has scrolled back and loaded older history, `messagesChanged` replacing the array with the newest 50 would drop the loaded history until they scroll again. Realtime is primary so this is an edge case, but worth a glance when you next touch the chat client.

### N6 (informational) — `npm audit` is back up to 13 (from the 12 at my first audit)
A commit correctly cleared the safely-fixable advisories down to 9, but new advisories published against `next@14.2.35` since have pushed it back to 13 (7 high, 6 moderate). **This is expected drift** — a pinned framework version accumulates disclosures over time; it's not a regression in your code. The runtime-relevant ones are all Next.js (cache confusion, RSC DoS, image-optimizer DoS, and notably a **CSP-nonce XSS** one). `npm audit fix` (no `--force`) clears the non-Next transitive ones. The real fix remains the **Next 15/16 upgrade**, still pending — and it's now more attractive because it also unblocks the nonce CSP (L6). Treat it as a scheduled pre-launch task with a regression pass, not a rush.

## 5. Load & scale readiness (updated)

The architecture that was sound is still sound, and several of the things I flagged as "first to break" are now fixed:
- **Notification fan-out** is awaited and chunked (was fire-and-forget) — ✅.
- **The unread N+1** is one grouped query — ✅.
- **The one-request feed DoS** is bounded — ✅.
- **Rate limiting** is now distributed, so it actually holds across instances — ✅.
- **Analytics** aggregates in the DB instead of loading every member into memory — ✅.

**What I'd still want proven by an actual load test before the full 1,000-member migration** (the 20-creator test won't surface these):
1. **300 concurrent on the community feed + a chat room simultaneously, while an admin publishes a campaign.** This is where the notification fan-out, the feed query, the rate limiter, and the `max:1` connection pool interact. Still the single most important test.
2. **Realtime ping storm.** Confirm the client throttle (H6) actually caps refetch rate under a busy room, and confirm the Supabase Realtime RLS lock-down so the ping channel can't be driven by an outsider.
3. **Vercel Pro must be live before the test**, or the 10s Hobby function timeout will distort everything (and would itself break the cron fan-out).
4. **Upstash capacity:** the login path now does 2-3 Redis round-trips per attempt. At migration-day login volume (1,000 people signing in over a morning) that's well within free-tier limits, but confirm the plan's request ceiling.

**First thing likely to break under load:** still the Supabase compute tier, not the app code — the `max:1` pooling means you're bounded by the pooler's client slots against `max_connections`. That's a dial you turn (compute tier), not a code change, but turn it *before* migration and validate with the test above.
